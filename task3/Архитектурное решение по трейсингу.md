список данных, которые должны попадать в трейсинг:
1. ID – trace_id, span_id и тд 
2. Метки времени 
3. Контекст запроса – user_id, session_id, и тд 
4. Статус ответа/ошибки – status_code, error_code,error_message, stack_trace
5. Информация об окружении – host, environment


## Мотивация

1. Экономия времени разработчиков, более простой анализ проблем особенно для медленных запросов
2. Повышение SLA
3. Уменьшение времени реагирование на инциденты
4. Улучшение клиентского опыта за счёт повышения отказоустойчивости и снижения времени ответоа
5. Снижение финансовых потерь из-за простоев
6. Снижение затрат на разработку

## Предлагаемое решение

Этап 1 - OpenTelemetry для сбора телеметрии, Jaeger для визуализации трейсов, каждый запрос будет получать уникальный trace_id, а подзапросы span_id. Для внедрения необходимо разработать общую библиотеку по принципам чистой архитектуры, используя OTel SDK, затем настроить экспорт трейсов в Jaeger. При наличии ресурса рекомендуется подключить также трасеровку в Sentry, чтобы иметь полную картину с фронта до бека. 
При подозрении на медленные запросы в БД, подключить также трейсинг через SQLAlchemyInstrumentor. 
При задержках в очередях или для нахождения потерянных/застрявших сообщений подключить трейсинг к RabbitMQ через opentelemetry-instrumentation-rabbitmq

## Компромиссы

1. Нет большого смысла внедрять трейсинг в монолитном приложении, тк все выполняется в одном процессе
2. При отсутствии проблем с производительностью БД, задачу по подключение БД к трейсингу можно положить в техдолг
3. При отсутствии проблем с очередями, задачу по подключение RabbitMQ к трейсингу можно положить в техдолг
4. Когда проблему проще воспроизвести руками, системы с небольшой нагрузкой или простые системы без БД и очередей
5. Если система высоконагруженная и для хранения трейсинга необходимы терабайты данных, необходимо очень тщательно выбирать что именно необходимо мониторить
6. Если нет проблем со скоростью ответа, локализацией багов и нет желания выкинуть лишние деньги то не стоит внедрять трейсинг

## Безопасность

1. Внедрение аутентификации через Keycloak — зайти в систему смогут только сотрудники компании с актуальной учетной записью и ролью “Поддержка”
2. Доступ к Jaeger только из-под впн
3. Маскирование, обезличивание данных
4. Экспорт только для супер админов, доступ к БД только для админов
5. Шифрование данных
6. Логирование кто и когда просматривает данные, внедрение алертинга + ограничение на просмотр данных, Splunk для детектирования аномалий
7. Автоматическое удаление трейсов старше n дней (хранить столько же сколько и логи)
