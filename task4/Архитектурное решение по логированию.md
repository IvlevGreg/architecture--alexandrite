## Cписок необходимых логов

[Схема](jewerly_c4_model_4.1.drawio)

Пояснение к схеме – в целой реализации необходимо иметь возможность установить лог в любом месте приложения для локализации проблемы, 
даже если нет необходимости в постоянных info логах все равно потенциальные простои из-за невозможности без дополнительных логов на продакшене 
локализовать проблему могут стоить слишком дорого.

### Info логи:

| Что логируем                                | Параметры                                                                                               | 
|---------------------------------------------|---------------------------------------------------------------------------------------------------------|
| Ошибки пользователей                        | базовый набор для Sentry (или аналог) user_id, версия браузера + ОС, YM_clientId действия на сайте и тд |
| Взаимодействие с заказом создание/изменение | время, user_id,YM_clientId, номер заказа                                                                |
| Загрузка/получение 3D-модели                | Id 3d модели, user_id,YM_clientId, формат файла, размер                                                 |
| Расчет стоимости                            | Id 3d модели, user_id,YM_clientId, цену                                                                 |
| Журнал запросов к БД                        | Стандартные Postgre                                                                                     |
| Журнал событий брокера                      | Стандартные RabbitMQ                                                                                    |


Помимо info логов необходимо собирать еще Error/warn для поиска ошибок и debug для локализации нестандартного поведения

### Error/warn логи:


| Что логируем                                                       | Параметры                                                                               | 
|--------------------------------------------------------------------|-----------------------------------------------------------------------------------------|
| Все 400/500 ошибки                                                 | ответ, body, url запроса + то что важно в конкретном случае (user_id,YM_clientId, и тд) |
| Любое неожиданное поведение (пустой ответ, неожидаемый ответ и тд) | ответ, body, url запроса + то что важно в конкретном случае (user_id,YM_clientId, и тд) |


## Мотивация 

Метрики на которые повлияет внедрение логирования:

1. Повышение уровня SLA (процент заказов, выполненных в срок)
2. Согласно отчету [Gartner](https://sky.pro/wiki/analytics/elk-logirovanie-effektivnyj-sbor-i-analiz-dannyh-dlya-vashej-it-sredy/), компании, внедрившие централизованное логирование, демонстрируют на 43% более высокую скорость обнаружения и устранения инцидентов
3. Согласно [исследованиям](https://sky.pro/wiki/analytics/elk-logirovanie-effektivnyj-sbor-i-analiz-dannyh-dlya-vashej-it-sredy/), компании, внедрившие ELK, отмечают сокращение времени на диагностику проблем в среднем на 60%
4. Повышение безопасности логи фиксируют действия пользователей и внешний трафик, что позволяет проще выявлять, угрозы и блокировать их

Очередность реализации логов:
1.  MES API – чтобы максимлаьно быстро разобраться с вопросами задержки расчёта и обработки заказов (начинать с обработки заказов)
2. RabbitMQ – понять теряются или зависают заказы 
3. CRM API – тоже могут возникать задержки или потеря заказа

## Предлагаемое решение 
[схема](jewerly_c4_model_4.2.drawio)
Для внедрения логов планируется использовать ELK-стек, куда отправлять логи со всех систем компании:

1. Развернуть ELK стек
2. MES API и CRM API – доработка логирования — внедрение общих билблиотек, интеграция с traceId 
2. RabbitMQ – включить логи, audit message log, отправлять логи в Elastic
3. 

### Политика безопасности

1. В логах не должны содержаться перс данные позволяющие идентифицировать пользователя любая пара данных – ФИО, телефоны, емеил и тд 
2. Воможно маскирование полей на стадии логгирования
3. KeyLock или аналог с ролевой моделью для доступа к логам 
4. Действия с логами журналируются
5. Доступ в Kibana только из VPN

### Политика хранения

1. Отдельные индексы на каждый сервис
2. Срок хранения 7 дней для info и 14 для error
3. Логи не архивируются, без законодательной необходимости для экономии средств 

### Необходимые мероприятия для превращения системы сбора логов в систему анализа логов:

1. Внедрить алерты на основе логов и метрик
2. Внедрить правила работы с алертами
3. Внедрить инцидент менеджент
4. Внедрить поиск и автоматизацию выявления аномалий
5. Сделать интеграцию с системой где происходит основное общение команлы (Слак, Пачка или аналог)
6. Построить универсальные дешборды по состоянию железа сервисов и специализированные по сервисам
7. Внедрить отчеты в командах
